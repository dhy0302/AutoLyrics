# AutoLyrics 性能审查报告

审查时间：2026-10-03 ·代码基线 `a07df5f`（v1.12.0-build33）

方法：静态审查全部 44 个 Kotlin 文件，逐条核实到具体行号。**未修改任何代码。**

---

## 摘要

代码整体质量不错——**缓存有界、线程池收敛、逐字动画已正确解耦、Bitmap 已降采样**，
这些都是容易踩坑的地方，作者都处理了。

但有 **3 个真实问题**，其中 1 个每帧影响整个歌词页，1 个影响切歌响应速度。

| # | 问题 | 影响 | 成本 |
|---|---|---|---|
| **1** | 高频位置流让整个歌词页重组 10~20 次/秒 | 持续耗电、后台降频 | 低 |
| **2** | 通知回调在主线程做 Binder 全量读取 | 偶发掉帧 | 低 |
| **3** | 全局 Mutex + 阻塞式HTTP，切歌最长被堵 10 秒 | 切歌慢 | 中 |

## 问题 1：高频状态流让整个歌词页重组（建议优先修）

### 位置

`ui/screen/HomeScreen.kt:169`

```kotlin
val lyricPosition by LyricEngine.lyricPositionMs.collectAsState()
```

发射点在 `lyric/LyricEngine.kt:86`，跟随 ticker，**每秒 10~20 次**（由`precisionMode.pollMs` 决定）。

### 为什么是问题

这个值最终只被**当前行**消费，而且**只当基准值用一次**：

`HomeScreen.kt:938` → `rememberKaraokeClock(positionMs = positionMs)`

而 `KaraokeClock.kt:90` 的逐帧推进走的是 `withFrameNanos`，**完全不依赖这个 flow**。

也就是说：**每秒 10~20 次更新，对逐字动画毫无作用。**

但它挂在 `HomeScreen` 顶层，而 `HomeScreen` 包含：
- 流体渐变背景（`AlbumBackdrop`，588 行）
- 专辑封面 + Palette 提取
- 播放控制条
- 歌词列表（`AppleLyricList`）

`AppleLyricList` 内部虽有 `positionMs = if (active) positionMs else 0L`（`:850`）的优化，
但**顶层 Composable 已经重组了** —— 优化只挡住了列表内部的重组，没挡住父级。

作者显然意识到过频率问题：`PlayerBar.kt:70` 的注释写着
「原来直接用 positionMs（每 100ms 变一次），Slider 也就每 100ms 重建一次」，
并做了 `/1000*1000` 取整。**但只解决了下游，没解决上游** —— 顶层仍在重组。

`OverlayContent.kt:67` 有同样问题（悬浮窗整体重组）。

### 修法

把高频值从重组树里摘出去，改为 lambda 读取。

```kotlin
// LyricEngine.kt —— 新增：只要基准值，不要高频流
val lyricPositionSample: () -> Long get() = { _lyricPositionMs.value }
```

`HomeScreen.kt` 删除 `:169` 那一行collectAsState，
把 `AppleLyricList` 的 `positionMs: Long` 参数改成 `positionMs: () -> Long`。

`AppleLyricLine` 内部（`:940`）改成：

```kotlin
val smoothPosition by rememberKaraokeClock(
    active = karaoke,
    positionMs = positionMs(),   // 关键：只在时钟启动那一刻读一次
    playing = playing,
)
```

`rememberKaraokeClock` 本来就只取一次基准，改成 lambda 不影响其语义。

**收益**：歌词页每秒少10~20 次全页重组，只在真正换行时重组。
**成本**：约 20 行改动，涉及 3 个文件。

## 问题 2：通知回调在主线程做 Binder 全量读取

### 位置

`media/MediaNotificationListener.kt:88`

```kotlin
if (MediaSessionWatcher.snapshots().any { it.pkg == sbn.packageName }) return
```

`snapshots()`（`MediaSessionWatcher.kt:255`）会遍历所有 controller，
每个读 `metadata` + `playbackState` —— **两次跨进程 Binder，同步等待**（`:336-345`）。

`NotificationListenerService` 的回调**默认在主线程**。

### 为什么是问题

媒体 App 更新进度时通常**每秒重发一次通知**。
于是：**每秒主线程一次全量 Binder 读取**，N 个播放器 × 2 次 IPC + Bundle 反序列化。

`PlaybackMonitor.kt:85-98` 有大段注释说明「ticker 搬到 IO 线程，避免每秒 10~20 次同步 IPC 压主线程」——
**但回调路径没跟上**：`MediaSessionWatcher.kt:196/243` 的
`registerCallback(callback, handler)` 里的 `handler` 仍是 `Looper.getMainLooper()`（`:57`），
所以换歌时主线程照样跑一遍完整 `update()`。

### 修法

```kotlin
// MediaSessionWatcher.kt —— 判定不需要读 metadata，controllers 的 key 就是 "pkg#token"
fun hasSessionFor(pkg: String): Boolean =
    controllers.keys.any { it.substringBefore('#') == pkg }
```

```kotlin
// MediaNotificationListener.kt:88
if (MediaSessionWatcher.hasSessionFor(sbn.packageName)) return   // 零 Binder
```

```kotlin
// MediaSessionWatcher.kt —— 回调改到 IO 线程派发，与 ticker 统一
private val cbHandler = Handler(Dispatchers.IO.asHandler())
// :196 / :243 两处
registerCallback(callback, cbHandler)
```

## 问题 3：全局 Mutex + 阻塞式 HTTP，切歌最长被堵 10 秒

### 位置

`lyric/LyricRepository.kt:82` + `:112-118`，`util/Http.kt:47`

```kotlin
private val lock = Mutex()// 进程级单锁，粒度是「一首歌」而非「一个 key」

return lock.withLock {
    memory[key]?.takeIf { !forceRefresh }?.let { return@withLock it }
    val result = fetchFromNetwork(track, order)   // 整个多源回退链都在锁内
    memory[key] = result
    writeCache(key, result)                      // 磁盘写也在锁内
    result
}
```

```kotlin
// Http.kt:47 —— 阻塞 execute()，协程取消进不去
client.newCall(builder.build()).execute().use { ... }   // TIMEOUT_SEC = 10L
```

### 为什么是问题

1. 锁内最坏跑**约 32 次串行 HTTP**（搜索 + 3 候选取词+ 繁简双变体，多源回退）
2. `LyricEngine.fetch` 切歌时 `loadJob?.cancel()`（`LyricEngine.kt:118`），
   但**取消进不去 `execute()`** —— 只有 socket 超时（10 秒）才恢复
3. 于是：歌曲 A 持锁跑 → 歌曲 B 卡在 `lock.withLock` → **B 的歌词最多 10 秒后才出现**

快速切歌/连播歌单时这是必现的。

### 修法

**（a）锁按 key 降粒度，磁盘写挪出锁：**

```kotlin
private val locks = ConcurrentHashMap<String, Mutex>()
private fun lockFor(key: String): Mutex = locks.getOrPut(key) { Mutex() }

return lockFor(key).withLock {
    memory[key]?.takeIf { !forceRefresh }?.let { return@withLock it }
    val result = fetchFromNetwork(track, order)
    memory[key] = result
    result
}.also { writeCache(key, it) }
```

**（b）HTTP 改可取消：**

```kotlin
suspend fun get(url: String, headers: Map<String, String> = emptyMap()): String =
    suspendCancellableCoroutine { cont ->
        val call = client.newCall(buildRequest(url, headers))
        cont.invokeOnCancellation { call.cancel() }   // 旧歌立刻中断，不占着锁
        call.enqueue(object : Callback {
            override fun onFailure(call: Call, e: IOException) {
                if (!cont.isCancelled) cont.resumeWithException(e)
            }
            override fun onResponse(call: Call, response: Response) {
                response.use { r ->
                    if (!r.isSuccessful) cont.resumeWithException(IOException("HTTP ${r.code}"))
                    else cont.resume(r.body?.string() ?: error("empty body"))
                }
            }
        })
    }
```

## 次要问题（可暂不做）

### 4. 缓存 TTL 判定顺序颠倒

`LyricRepository.kt:311`：先 `file.readText()` + `JSONObject` 全解析，`:318` 才判 TTL。

过期条目等于「先付一次全量磁盘 I/O，再付一次全量网络 I/O」。

**修法**：改用 `file.lastModified()` 判 TTL，一次 stat 零读取。

### 5. 繁简双变体导致请求数翻倍

`LyricRepository.kt:217`：`searchVariants(track)` 在每个源的循环体内，
繁体歌名会让**所有源**的请求数 ×2。而 `searchByHash` 对两个变体返回的 FileHash 几乎必然相同。

**修法**：变体 2 只在变体 1 完全失败时才试。

### 6. `TextMatch.normalize` 每次 `new Regex`

`util/TextMatch.kt:39`：正则写在函数体内。每次调用重新编译 Pattern。
每首歌每源约 240 次调用 → 约 6000 次分配。

**修法**：提到 object 顶层（与已有的 SUFFIX/PUNCT 一致）。

### 7. 主线程初始化开销

`App.kt:31-32`：`mkdirs()` + 读 34KB raw 建 4200 项词表 + SharedPreferences 首次加载，全在主线程。
冷启动多 30~80ms。

**修法**：挪到后台协程。

### 8. `unescape` 的 8 次连续 `replace`

`lyric/parser/LyricParser.kt:127-135`：8 次 `replace` = 8 次全串拷贝，
且 `&#10;` 在歌词里几乎必然存在（等于稳定多 8 次全串分配）。

**修法**：单遍扫描，只在真有 `&` 时建 StringBuilder。

### 9. `SettingsStore.save()` 无防抖

`util/SettingsStore.kt:208`：每次 `update` 全量序列化 30 字段。
拖动「全局偏移」滑块 = 每帧一次全量 JSON 序列化 + SharedPreferences 写。

**修法**：加 300ms 防抖。

### 10. Bitmap recycle 策略不一致

`MediaSessionWatcher.kt:163/206/251` 主动 `recycle()` 封面，
与 `PlaybackMonitor.kt:215-218` 注释明确禁止的做法冲突：

> v1.8.2：这里曾尝试 recycle 封面释放内存，但 UI 侧可能仍持有引用，
> 重组慢一帧就会崩在 "trying to use a recycled bitmap"

`AlbumArt.downsample` 返回的新 Bitmap 正是被 recycle 的那份。
**这是潜在崩溃**，建议去掉三处 recycle。
